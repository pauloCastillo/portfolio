# Spec Delta

## Purpose

Muestra en el dashboard de administración métricas reales del contenido publicado y de la audiencia: cuántos blog-posts y proyectos están publicados y cuántos usuarios únicos visitaron el sitio, con su tendencia diaria.

## ADDED Requirements

### Requirement: Dashboard shows published blog-post count

The system SHALL display on the admin dashboard the count of blog-posts with `published: true`, derived from the same published-posts feed used by the public site.

#### Scenario: Published count matches public feed

- **WHEN** an authenticated admin opens `/admin/dashboard`
- **THEN** the blog-posts card shows a number equal to the count of items returned by the published-posts feed

#### Scenario: Drafts are excluded from the count

- **WHEN** an admin creates a draft post (`published: false`)
- **THEN** the dashboard blog-posts count does NOT increase

### Requirement: Dashboard shows published project count

The system SHALL display on the admin dashboard the count of projects with `published: true`, derived from the same published-projects feed consumed by the public projects section.

#### Scenario: Published count matches public section

- **WHEN** an authenticated admin opens `/admin/dashboard`
- **THEN** the projects card shows a number equal to the count of items returned by the published-projects feed

#### Scenario: Drafts are excluded from the count

- **WHEN** an admin saves a draft project (`published: false`)
- **THEN** the dashboard projects count does NOT increase

### Requirement: Public visit beacon records anonymous unique visitors

The system SHALL expose a public endpoint (no authentication required) that records a visit event carrying an anonymous `visitor_id` (UUID v4 generated by the client), the visited `path`, and a server-assigned timestamp. The public site SHALL send the beacon at most once per visitor session.

#### Scenario: First visit from a new visitor is recorded

- **WHEN** a public client sends a beacon with a `visitor_id` never seen before
- **THEN** the system responds `201` and the visitor counts as one unique visitor from that day forward

#### Scenario: Repeat beacon from the same visitor does not inflate uniques

- **WHEN** the same `visitor_id` sends additional beacons on the same calendar day
- **THEN** the system responds `201` and the unique-visitor count for that day is unchanged

#### Scenario: Malformed visitor identity is rejected

- **WHEN** a public client sends a beacon with a missing or non-UUID `visitor_id`
- **THEN** the system responds with a validation error and records nothing

### Requirement: Dashboard shows unique-visitor trend

The system SHALL expose an admin-only visit-stats endpoint returning unique-visitor counts for today, the last 7 days, and the last 30 days, plus a per-day series of unique visitors for the last 30 days. The admin dashboard SHALL render these as cards and a daily trend chart.

#### Scenario: Stats reflect recorded visits

- **WHEN** three distinct `visitor_id` values beacon today and an authenticated admin opens `/admin/dashboard`
- **THEN** the "today" unique-visitors card shows `3`

#### Scenario: Unauthenticated stats access is rejected

- **WHEN** a request without valid admin credentials hits the visit-stats endpoint
- **THEN** the system responds `401` and exposes no visit data

#### Scenario: Empty history renders zero state

- **WHEN** no visit has ever been recorded and an authenticated admin opens `/admin/dashboard`
- **THEN** the visitor cards show `0` and the trend chart renders an explicit empty state instead of failing

### Requirement: Visit tracking stores no personal data

The system SHALL NOT persist IP addresses, user-agent strings, or any client identifier beyond the anonymous `visitor_id`, the visited `path`, and the timestamp.

#### Scenario: Stored event contains only anonymous fields

- **WHEN** a beacon is recorded
- **THEN** the persisted event contains `visitor_id`, `path`, and timestamp and no IP address or user-agent data
